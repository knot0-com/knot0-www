## The Round-Trip Tax

Here's an agent finding broken services:

```
Turn 1  → tool: list_services()             → 47 services          → context
Turn 2  → tool: get_metrics("checkout")      → {errorRate: 0.12}   → context
Turn 3  → tool: get_metrics("payments")      → {errorRate: 0.03}   → context
Turn 4  → tool: get_metrics("auth")          → {errorRate: 0.08}   → context
  ... 44 more turns ...
Turn 48 → tool: get_dependencies("checkout") → [payments, auth, inventory] → context
Turn 49 → tool: get_dependencies("auth")     → [ldap, sessions]    → context
Turn 50 → "Based on my analysis..."
```

Fifty turns. Every result dumped into context. By turn thirty, the model has forgotten why it started. By turn fifty, it summarizes with the confidence of someone who read the Wikipedia abstract.

Here's the same task with a scratchpad:

```js
// Turn 1
const svcs = await db.query(`
  SELECT e.*, m.error_rate FROM entities e
  JOIN metrics m ON m.entity_id = e.id
  WHERE e.entity_type = 'service' AND m.error_rate > 0.05
`)
for (const s of svcs) {
  const deps = await db.query(
    `SELECT target_id FROM relations WHERE source_id = ?`, [s.id]
  )
  print(`${s.display_name}: ${s.error_rate} → ${deps.map(d => d.target_id).join(', ')}`)
}
```

```
Output:
  checkout: 0.12 → payments, auth, inventory
  auth: 0.08 → ldap, sessions
```

```
// Turn 2
"checkout and auth are degraded. checkout depends on auth,
 so auth is likely the root cause. Here's what I'd check..."
```

Two turns. Two lines of output in context. Done.

This isn't a trick. It's the end of a thread that runs through CodeAct, every coding agent you've used, and one paper from December that almost got it right.

## Step 1: Let Agents Write Code

In early 2024, Wang et al. published [CodeAct](https://arxiv.org/abs/2402.01030). The idea was deceptively simple: instead of forcing LLMs to pick from a tool menu, let them write and execute code.

```python
# CodeAct: the agent writes this, the framework runs it
import requests
response = requests.get("https://api.example.com/services")
services = [s for s in response.json() if s["error_rate"] > 0.05]
print(f"Found {len(services)} degraded services")
```

This was a genuine breakthrough. Code is a strictly more expressive action space than tool selection. You can query, filter, loop, and branch — all in one turn. Every tool call can be written as code. Not every program can be expressed as a tool call.

But CodeAct's code was **ephemeral**. Write a script, execute it, get the output, throw it away. The next turn starts fresh. No variables carry over. No state accumulates. Every turn is a standalone program.

This meant the agent had to rebuild its understanding from scratch on each turn, or stuff everything into context. The execution was powerful. The memory was gone.

## Step 2: Agents That Live in the Terminal

Then came the coding agents. Claude Code. Codex. Aider. Cursor. They took the code-execution insight and wired it to a shell.

```bash
# Claude Code: the agent runs bash commands
$ grep -r "error_rate" src/ --include="*.ts"
$ cat src/services/checkout.ts | head -50
$ npm test -- --grep "checkout"
```

This was the next step: agents that don't just write code, they *operate*. They read files, run tests, execute scripts, pipe output. The shell is their workspace.

But it's still ephemeral. Each command is a one-shot. The agent runs `grep`, gets the output in context, reasons about it, runs the next command. There's no persistent environment between commands. Variables don't survive. Intermediate results live only in the conversation history, which grows with every command.

These agents are powerful because they have the entire operating system as their action space. But their memory model is still the context window. Every `cat`, every `grep`, every test output — it all lands in context and stays there forever.

## Step 3: The RLM Paper

In December 2025, Zhang, Kraska, and Khattab published [Recursive Language Models](https://arxiv.org/html/2512.24601v1). The key insight: instead of ephemeral scripts, give the agent a REPL where variables survive across tool calls within a single task. The agent accumulates state — and because only `print()` output enters context, the intermediate state stays in the scratchpad, not in the conversation.

```js
// repl call #1: query and store
services = await db.query("SELECT * FROM entities WHERE entity_type = 'service'")
print(`Loaded ${services.length} services`)

// repl call #3: 'services' is still here
degraded = services.filter(s => s.error_rate > 0.05)
print(`${degraded.length} degraded`)
```

The results were striking. Fewer turns. Less context waste. Better accuracy on multi-hop reasoning tasks.

But the REPL was still **ephemeral across runs**. Each new task started a fresh environment. The agent could accumulate state brilliantly within a single conversation — but when that conversation ended, the scratchpad was wiped clean. The next invocation started from zero.

The paper framed this as sufficient. For benchmark tasks with a clear start and end, it is. But for agents that live longer than a single request — agents that monitor, learn, and adapt over hours and days — starting from zero every time is the same problem all over again.

We read the paper in January.

By February, we had shipped it as the primary agent loop in Knot0.

What we found surprised us.

## Step 4: REPL Is All You Need

We took the RLM insight and pushed it further: **the REPL persists across runs**.

When an agent finishes a run, we snapshot every variable in the `vm.Context` and store it in the actor's heap. When the agent wakes up again — minutes, hours, or days later — we restore the snapshot. The scratchpad picks up exactly where it left off.

```js
// Run 1 (Monday morning): agent monitors services
services = await db.query("SELECT * FROM entities WHERE entity_type = 'service'")
baseline = services.map(s => ({id: s.id, errorRate: s.error_rate}))
print(`Baseline captured: ${baseline.length} services`)

// Run 2 (Tuesday, triggered by alert): 'services' and 'baseline' are still here
current = await db.query("SELECT * FROM entities WHERE entity_type = 'service'")
drifted = current.filter(c => {
  const b = baseline.find(b => b.id === c.id)
  return b && c.error_rate > b.errorRate * 2
})
print(`${drifted.length} services degraded since baseline`)
```

This changes what a REPL agent can be. It's not just a smarter way to answer questions — it's a persistent process with working memory that outlives any single conversation.

Cross-run persistence alone would have been enough to change how we build agents. But it wasn't even the biggest finding.

The RLM paper positioned the REPL as a solution for a specific class of problems: long-context tasks. Knowledge graphs. Multi-hop retrieval. Tasks where tool-call agents drown in their own context.

What we found is that the REPL isn't a specialized mode for hard problems. It's the better default for *everything*.

Simple tasks. Complex tasks. Tasks with one lookup and tasks with fifty. The REPL wins across the board — not because it's smarter, but because it changes what "one turn" means.

In a tool-call agent, one turn = one action. Read a file. Run a query. Call an API. The model does one thing, sees the result, decides what to do next.

In a coding agent, one turn = one command. Run grep. Run a test. Cat a file. More expressive than a tool call, but still one shot per turn.

In a REPL agent, one turn = a program. The model writes code that does ten things, sees only what it chose to `print()`, and decides what to do next based on the summary it wrote for itself.

The progression looks obvious in hindsight:

| Generation | Action space | Memory | Context cost |
|-|-|-|-|
| Tool-call agents | Pick one tool | None | Every result, forever |
| CodeAct | Write a script | None (ephemeral) | Script output, forever |
| Coding agents (Claude Code, Codex) | Shell commands | None (ephemeral) | Every command output, forever |
| RLM (paper) | REPL ephemeral | Within-run only (wiped between tasks) | Only `print()` output |
| **REPL-primary (Knot0)** | **REPL persistent** | **Persistent across runs (heap snapshot)** | **Only `print()` output** |

Each step added something. CodeAct added code. Coding agents added the OS. RLM added the print contract and within-run memory. We added cross-run persistence and the conviction that this isn't a mode — it's the whole architecture.

## How Code Execution Evolved

Agents have been writing code for a while. The question was always what happens to it afterward.

**CodeAct** (Wang et al., 2024) was the first to say: let the agent emit code instead of picking from a tool menu. The agent writes a Python script, the framework executes it, the output goes back to the model. But each script is fire-and-forget. Variables don't survive. The next turn starts from a blank slate.

**Coding agents** — Claude Code, Codex, Aider, Cursor — took this further by giving the agent a shell. Now it could read files, run tests, pipe commands. The entire OS became the action space. But the execution model was the same: each command is ephemeral, every output lands in context, nothing persists between invocations.

**RLM** (Zhang, Kraska, Khattab, 2025) changed the memory model. Instead of throwaway scripts, the agent gets a REPL — a persistent environment where variables survive across tool calls within a single task. And only `print()` output enters context. This was the first architecture where the agent could accumulate working state without paying the context cost. But when the task ended, the REPL was destroyed. Next task, clean slate.

**REPL-primary** (what we built) removes that last boundary. The REPL persists across runs. The agent's scratchpad survives between conversations — variables snapshot to the actor heap on completion, restore on the next wake-up. And the scope isn't limited to long-context tasks. It's the default loop for everything.

## The Print Contract

Here's the mechanism that makes everything work.

In a tool-call agent, every tool result enters the conversation. The model calls `read_file("config.yaml")` and the entire file — 200 lines — lands in context. Permanently. The model can't unsee it. Even if it only needed one field.

In a REPL agent, nothing enters context except what the agent explicitly `print()`s.

```js
const config = JSON.parse(await fs.read("config.yaml"))
const deps = await db.query(
  "SELECT * FROM relations WHERE source_id = ?", [config.serviceId]
)
const metrics = await db.query(
  "SELECT * FROM metrics WHERE entity_id IN (?)",
  [deps.map(d => d.target_id)]
)

// 200 lines of config, 47 relations, 200+ metric rows — all processed.
// None of it enters context. Only this:
print(`${deps.length} dependencies. ${metrics.filter(m => m.error_rate > 0.05).length} degraded.`)
```

Output: `47 dependencies. 3 degraded.`

That's what the model sees on the next turn. Seven words. Not the config file, not the dependency graph, not the raw metrics. Seven words that the agent chose to remember.

The agent is its own summarizer. It reads everything, processes everything, and decides what matters enough to carry forward. The rest vanishes.

Tool-call agents are cameras. They capture everything and hope the model can find what matters in the footage. REPL agents are writers. They take notes.

## Composition Is The Point

A tool-call agent sees a menu. Seventy-two tools. Pick one per turn. Can't combine them. Can't filter results before returning them. Can't loop.

A REPL agent sees a programming environment:

```js
// Query, filter, enrich, summarize — one turn
const broken = await db.query(`
  SELECT e.*, m.error_rate FROM entities e
  JOIN metrics m ON m.entity_id = e.id
  WHERE m.error_rate > 0.05
`)

for (const svc of broken) {
  const analysis = await llm_query(
    `What could cause elevated errors in a ${svc.properties.tech_stack} service?`,
    JSON.stringify(svc)
  )
  print(`## ${svc.display_name}\n${analysis}\n`)
}
```

Query. Filter. Loop. Sub-LLM call per result. Formatted output. One turn.

The agent didn't pick a tool. It wrote a program. And the program did things no tool menu could express: a filtered query joined with metrics, iterated with per-item LLM analysis, formatted for human consumption.

This is why the REPL wins even on simple tasks. Even a two-step task — read a file, extract a value — benefits from not polluting context with the entire file. The agent reads it inside the REPL, extracts what it needs, prints the answer. The file never enters the conversation.

The simpler the task, the more wasteful the tool-call overhead looks.

## What Comes After

Once the REPL is the default loop, other things become possible.

Agents that persist across sessions — not by cramming history into a prompt, but by storing state in variables and databases that outlive any single conversation. Agents that hand off work to other agents by writing to shared groups, not by serializing context into tool calls. Agents that improve themselves by running evaluation loops in the same REPL environment they use for real work.

The scratchpad turns out to be the foundation, not the ceiling. But that's a different post.

For now: write code, execute it, print what matters, carry state forward. Let the context window hold reasoning, not raw data.
